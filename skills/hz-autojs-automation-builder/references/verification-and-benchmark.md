# 同步、首跑、基准与回归

生成完不等于能用。项目必须经过「分级首跑 → 业务验收 → 基准 → 固定回归」四段，缺一段就只能算候选。

## 一、同步

**前置检查（2026-10-01 实测）**：若 V5 开启了 Web 登录保护，`project_sync_push` 会在设备端下载阶段对每个文件返回 `下载失败，HTTP状态: 401`。根因是设备侧 `fileManager` 直接 GET 公共库下载地址、不带任何 token，而 V5 `ServiceAccessFilter` 只放行 `access` / `health` / `runtime` 等公开路径。此时不要反复重推（每推一次都会重新建一次设备端目录），按下列顺序处置：

1. 确认 V5 设置里的 Web 登录保护状态；临时关闭后再推，推完按需恢复。
2. 或改由已登录的 V5 界面做目录下发。
3. 小文件集合（探针、单模块）可用 `device_file_write_text` 直写设备路径做验证；大项目不要用这条路。
4. 长期方案是 V5 为设备文件下发补签下载票据（与本技能同批记录为 V5 侧缺口）。

1. `project_sync_plan`：按本地项目相对最近一次同步基线的变化，输出新增 / 修改 / 删除候选 / 冲突（不检测设备端外部改动）。
2. `project_sync_push`：按**显式清单**推送。一次同步只提交一个设备任务（设备端只弹一次目录下发窗口）。
3. `project_sync_status`：核对本地基线版本与最近同步结果；部分成功必须如实记录为部分成功。
4. `mirror_delete` 默认关闭。远端有本地不存在的文件时，先确认它们是不是设备端运行记录（`runs/`），不要为了「干净」删掉证据。

## 二、分级首跑

只有 `readiness=ready`（带任务卡且 `--check` 通过）的任务才能进入首跑；partial / blocked 任务运行会返回 `NOT_READY`，不要把它们当候选。

| 级别 | 跑什么 | 成功判据 | 失败处置 |
| --- | --- | --- | --- |
| L1 只读 | `bootstrap` / `detect-state` | 返回分辨率、契约 baseline、残差在容差内；状态识别命中 `verified` 状态的锚点 | 契约或检测通道问题，回到契约修，不改业务代码 |
| L2 单动作 | 一个写入型任务单次执行 | 动作后锚点变化 + verify 判据全部通过（marker 只在此时发出） | 停在原状态，留截图与 OCR，人工/AI 诊断 |
| L3 限次循环 | `runLoop(maxSteps)`，先给很小的上限 | 每步转移都在 `next[]` 里；命中 `stopMarkers` 正常停 | 出现未知状态即停并升级 |
| L4 复跑 | 同样输入重复一次 | 结果一致（同样的状态链、同样的数值方向），耗时在基准范围内 | 结果不一致就按不稳定处理，不进回归集 |

L1 通过前不要跑写入型任务；L2 通过前不要开循环。

## 三、业务验收

脚本 `SUCCEEDED` 只代表执行完毕，业务成功必须另判：

- **锚点判据**：目标状态的关键文本 / 数值出现（如剩余次数 20 → 15）。
- **资源判据**：顶栏资源或面板数值按预期方向变化（贡献 +3100、金币增加、紫晶卡不变）。
- **状态判据**：任务卡从 `领取` 变 `已完成`；关卡从 `挑战` 变 `扫荡`。
- **反向判据**：不该变化的资源（尤其是紫晶卡）没有减少。付费与消耗入口被守卫拦下时，必须能在运行记录里找到拒绝条目。

`verification.successMarkers` 里的每个标记都要有对应的 `verify` 判据实现；只打标记不算验收。生成器会把「没有就绪任务实现的 successMarker」列入 `uncoveredMarkers`，把「没有就绪任务消费的守卫」列入 `uncoveredGuards`，两者在首跑前必须清零或明确接受为未实现能力。

另外要留一组**判据失败样本**：数值方向不符或锚点未出现时，任务必须 `ok=false` 且 marker 为空。

## 四、基准指标

| 指标 | 采集方式 | 首版目标 |
| --- | --- | --- |
| 端到端耗时 | 宿主提交任务到终态的墙钟时间 | 记录基线，不做硬性上限 |
| 脚本内耗时 | 脚本自报 `RESULT: elapsedMs` | 与端到端差值反映传输与排队开销 |
| AI 调用次数 | 稳定运行期统计 | 0（只有未知状态升级才允许 >0） |
| 失败恢复次数 | 运行记录里的恢复条目 | 越小越好；同因恢复重复出现要固化成规则 |
| 截图 + OCR 次数 | 运行记录统计 | 每次状态判定 1 次；步数越多越要向「只 OCR 关键区域」优化 |

基准值写进项目 `runs/` 与探索运行记录的 `findings.md`，不要只留在聊天里。

## 五、固定回归清单

回归集只收**稳定可重复**的任务，首版至少覆盖：

1. `bootstrap` + `detect-state`：在目标应用主界面命中 `verified` 状态。
2. 一个只领取任务（挂机收益 / 里程碑 / 境界三选一）。
3. 一个消耗型任务（免费捐献 / 免费扫荡 / 血精凝练）：验证三层守卫——元素文本、点击落点 OCR、数值不足时拒绝执行；拒绝记录必须可在 `runs/` 里查到。
4. 一个弹层恢复场景：人为制造奖励弹层或教程提示，验证恢复路径。

每次回归产出：

```json
{
  "runId": "<时间戳>",
  "project": "<项目名>",
  "task": "<任务名>",
  "level": "L1|L2|L3|L4",
  "result": "ok|failed|stopped",
  "markers": ["..."],
  "elapsedMs": 0,
  "aiCalls": 0,
  "recoveries": [],
  "evidence": ["screenshots/..."]
}
```

追加写入，不覆盖历史；失败样本与成功样本一起保留。

## 六、什么时候算完成

- L1–L4 全过，且回归清单里的任务在同一天内至少复跑一次结果一致。
- 稳定运行期 AI 调用次数为 0；出现未知状态时能停机留证据，而不是盲点。
- 所有未验证项写在项目 README 的「未完成」段、`agent/manifest.json` 的 `missingEvidence` 与 `project-request.openGaps` 里。
- 没有任务卡的脚本保持 `partial / blocked`，不得因为「能生成占位」就进入回归集。
- 生成物、契约快照、运行记录三者能互相对上（`config/generated.json` 的 sha256 与实际输入一致）。
